# بررسی پاسخ 403 و گزارش صحیح Inspector

[بررسی سورس پروژه‌های مشابه و نتیجه پژوهش](INSTAGRAM_403_RESEARCH_FA.md) تفاوت تحلیل محتوا، API مجاز و صفحه بازیابی را با منابع مشخص توضیح می‌دهد. کد متن‌باز مشابه به‌تنهایی رفع 403 این مقصد را تضمین نمی‌کند.

این اصلاح مربوط به دستور ادمین /instagram برای یک صفحه ثابت است. هیچ نام کاربری نمی‌گیرد، فرم یا درخواست بازیابی ارسال نمی‌کند و اطلاعات تماس یا هویت حساب را استخراج نمی‌کند. این تغییر کد به‌تنهایی مشکل دسترسی زنده را رفع نمی‌کند.

## رفتار جدید

- روی پاسخ HTTP ناموفق، سرویس شمارش فیلد/دکمه را انجام نمی‌دهد و مقادیر صفر ساختگی تولید نمی‌کند.
- پیام 403 می‌گوید درخواست رد شده و علت دقیق نامعلوم است؛ تعداد عناصر گزارش نمی‌شود.
- پیام 429 محدودیت درخواست را نشان می‌دهد. هیچ retry خودکار اضافه نشده است.
- پاسخ خالی، خطاهای دیگر HTTP و پاسخ موفق جدا گزارش می‌شوند. بررسی صفحه موفق همچنان تعداد عناصر را نشان می‌دهد.
- قفل تک‌مرورگر، timeout، پاک‌سازی مرورگر، کنترل ادمین و گفت‌وگوی خصوصی حفظ شده‌اند. پرداخت، ایمیل و SARPI تغییر نکرده‌اند.

## تشخیص محدود روی سرور

دریافت 403 یعنی یک پاسخ HTTP دریافت شده است؛ علت قطعی، منبع رد درخواست یا مشکل IP از همین وضعیت قابل تعیین نیست. پاسخ ممکن است از مقصد یا واسط شبکه آمده باشد. صفر فیلد روی یک صفحه خطا درباره حساب‌ها چیزی ثابت نمی‌کند. موفقیت CDN دانلود مرورگر، موفقیت اینستاگرام را اثبات نمی‌کند.

برای مقایسه یک GET عادی با گزارش مرورگر، مدیر می‌تواند فقط یک بار دستور زیر را در PuTTY اجرا کند. این فرمان بدنه و cookie چاپ نمی‌کند، redirect را دنبال نمی‌کند، retry ندارد و proxy و اعتبارسنجی TLS را حفظ می‌کند. هیچ فایل، سرویس، تنظیمات شبکه یا دیتابیسی تغییر نمی‌کند:

```bash
curl --silent --show-error --max-time 20 \
  --output /dev/null \
  --write-out 'HTTP: %{http_code}\nTLS_VERIFY: %{ssl_verify_result}\n' \
  'https://www.instagram.com/accounts/password/reset/'
```

این یک درخواست واقعی و محدود به صفحه ثابت است، نه تست حساب. درخواست HEAD برای مقایسه رفتار GET مرورگر کافی نیست.

| خروجی | تفسیر محدود |
|---|---|
| 403 و TLS_VERIFY=0 | همین GET هم رد شده است؛ علت قطعی مشخص نیست. اعتبارسنجی TLS موفق، سلامت دسترسی صفحه را تضمین نمی‌کند. |
| 200 | فقط پاسخ اولیه GET موفق است؛ ممکن است صفحه دیگری، challenge یا ساختار متفاوت باشد. به معنی رفع خطای مرورگر نیست. |
| 3xx | این GET به پاسخ redirect رسیده؛ بدون بررسی مقصد و محتوا نتیجه فرم مشخص نیست. |
| 429 | بررسی‌ها را پشت‌سرهم تکرار نکنید؛ محدودیت درخواست ثبت شود. |
| 000 یا خطای TLS/timeout | این اجرا پاسخ HTTP معتبر نگرفته؛ مسیر شبکه/TLS باید با تنظیمات مجاز بررسی شود. |

بدنه صفحات، Set-Cookie، خروجی کامل env، کلیدها یا رمزها را برای تشخیص ارسال نکنید. در محدودیت پایدار، از پشتیبانی رسمی سرویس/شبکه برای بررسی دسترسی مجاز استفاده شود؛ این ماژول راه رفع challenge یا تضمین حذف 403 ارائه نمی‌کند.

## نصب

اعتبارسنجی این اصلاح در محیط توسعه: کل ۱۴۰ تست موفق، pip check موفق و diff بدون خطای whitespace بود. پس از افزودن سناریوی پاسخ 403 به fixture مرورگر واقعی، ۱۷ تست runtime نیز موفق شدند. همه درخواست‌های مرورگر آزمون به loopback بودند؛ درخواست زنده Instagram از این محیط اجرا نشد. اعتبارسنجی این نسخه اصلاح‌شده روی Ubuntu مقصد هنوز انجام نشده است.

اصلاح گزارش روی شاخه feature/instagram-page-inspector آماده می‌شود و هنوز روی سرور فعال نصب نشده است. ZIP d2dfd8b و checksum آن ثابت‌اند. فایل‌های source یک stage تأییدشده را درجا ویرایش نکنید؛ manifest و ready.json نامعتبر می‌شوند. نصب نسخه جدید نیازمند بسته تازه، staging دوباره و بررسی baseline نسخه فعال فعلی است؛ صرفاً اجرای مجدد installer قدیمی برای این اصلاح مناسب نیست. PR merge نشده است.
