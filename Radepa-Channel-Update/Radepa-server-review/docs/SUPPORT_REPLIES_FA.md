# پاسخ مدیر به پیام پشتیبانی

این قابلیت روی شاخه feature/instagram-page-inspector آماده شده است. هنوز روی ربات فعال نصب نشده و PR merge نشده است. پس از نصب، پاسخ از خود ربات به کاربر می‌رسد؛ نام کاربری تلگرام برای دریافت پاسخ لازم نیست.

## روش‌های پاسخ

### ریپلای مستقیم

در گفت‌وگوی خصوصی مدیر با ربات، روی پیام «پیام پشتیبانی جدید» Reply کنید و پاسخ خود را بفرستید. متن یا رسانه قابل کپی توسط Telegram copyMessage، بدون لینک ارسال‌کننده اصلی، برای همان شناسه عددی ارسال می‌شود. موفقیت یعنی Telegram درخواست ارسال را پذیرفته؛ به معنی خوانده‌شدن پیام نیست.

### دکمه پاسخ

زیر اعلان پشتیبانی «↩️ پاسخ به کاربر» قرار دارد. با انتخاب آن، ربات پیام ForceReply با شناسه گیرنده می‌فرستد؛ روی همان پیام پاسخ دهید. برای انصراف از حالت Reply خارج شوید. حالت ورودی مخفی یا ارسال خودکار متن بعدی وجود ندارد.

### دستور برای ID یا username

```text
/reply 7000000123 سلام، پیام شما دریافت شد.
/reply @known_username متن پاسخ
```

نام مستعار دستور /supportreply هم فعال است. فقط کاربران موجود در دیتابیس ربات قابل انتخاب‌اند؛ این دستور ابزار جست‌وجوی افراد خارج از ربات نیست. شناسه عددی مبنای نهایی ارسال است.

برای username، تطبیق دقیق و بدون حساسیت به بزرگی حروف در کاربران ذخیره‌شده انجام می‌شود. اگر نتیجه یکتا باشد، با getChat روی ID شناخته‌شده، username فعلی بررسی می‌شود. نام تغییرکرده، نتیجه مبهم یا شکست API باعث توقف ارسال و درخواست بررسی شناسه عددی می‌شود. ربات با sendMessage به @username شخصی ناشناخته ارسال نمی‌کند.

پیام‌های قدیمیِ قبل از نصب لینک SQLite ندارند. ریپلای روی اعلان قدیمی ربات، راهنمای دستور /reply را نشان می‌دهد و شناسه از متن نقل‌شده استخراج نمی‌شود. برای این موارد گیرنده را شخصاً بررسی و ID را صریحاً در دستور بنویسید؛ مقادیر داخل نام یا متن کاربر قابل اعتماد نیستند.

## ذخیره‌سازی و دسترسی

- فقط ادمین‌های ADMIN_IDS در گفت‌وگوی خصوصی حق پاسخ دارند؛ کاربران عادی و گروه‌ها نمی‌توانند این مسیر را استفاده کنند.
- support_tickets فرستنده، شناسه پیام اصلی و زمان را نگه می‌دارد؛ support_deliveries ارتباط chat/message ادمین و ticket را نگه می‌دارد. بدنه پیام پشتیبانی در این جدول‌ها ذخیره نمی‌شود.
- این دو جدول افزایشی‌اند؛ کاربران، اعتبارها و سفارش‌های موجود بازنویسی نمی‌شوند. حذف کاربر، لینک‌های پشتیبانی او را cascade حذف می‌کند.
- لینک‌ها پس از Restart باقی می‌مانند و به context.user_data وابسته نیستند. ارسال پاسخ به پیام قدیمی پس از Restart نیز برای اعلان‌های ثبت‌شده کار می‌کند.
- reply router در گروه -3 و قبل از مسیر ایمیل/پرداخت/ورودی ادمین است. پاسخ شبیه ایمیل، متن منو یا عکس پاسخ نباید جست‌وجو، broadcast یا رسید پرداخت تلقی شود.
- متن نام کاربر و پیام با parse_mode=None ارسال می‌شود؛ علامت‌های Markdown یا HTML کاربر قالب‌بندی اعلان را خراب نمی‌کنند. پیام بلند به بخش‌های محدود تقسیم می‌شود و هر بخش لینک پاسخ مستقل به همان فرستنده دارد.
- اگر ارسال کامل به هیچ ادمینی موفق نباشد، کاربر پیام موفقیت نمی‌گیرد و امکان تلاش دوباره باقی می‌ماند. پیام ناقص ممکن است به ادمین رسیده باشد؛ این حالت تحویل کامل گزارش نمی‌شود.
- در مسدودبودن گفت‌وگو، Forbidden یا خطای Telegram، مدیر پیام عدم ارسال یا نامشخص‌بودن تحویل می‌گیرد؛ متن خام خطا و اطلاعات اتصال چاپ نمی‌شود. در timeout، retry خودکار انجام نمی‌شود؛ تکرار دستی می‌تواند پیام را دوباره ارسال کند، پس وضعیت را بررسی کنید.

## اعتبارسنجی و پذیرش

تست‌ها فقط با شناسه‌های ساختگی، SQLite موقت و mock تلگرام اجرا می‌شوند. پوشش شامل کاربر بدون username، ID بزرگ‌تر از ۳۲ بیت، ریپلای مستقیم، ForceReply، ماندگاری لینک، تفکیک ادمین‌ها، مجوز خصوصی، username تغییرکرده/مبهم، شکست ارسال، پیام بلند، failure ناقص و migration افزایشی است. یک آزمون با Application واقعی PTB و Telegram mock، عبور متن شبیه ایمیل و عکس پاسخ را از گروه -3 و جلوگیری از مسیرهای دیگر بررسی می‌کند. شبکه تلگرام و کاربر واقعی در این تست‌ها استفاده نمی‌شوند.

نتایج ۲۰۲۶-۱۱-۰۳: ۲۳ تست اختصاصی جدید اضافه شد. کل suite در محیط توسعه Python 3.12 برابر ۱۶۳ تست بدون failure/error/skip بود. کل suite در کانتینر تازه Ubuntu 22.04 و Python 3.10.12 با PTB 21.5 نیز ۱۶۳ تست بدون failure/error داشت؛ تنها یک تست Chromium سیستم به علت نبود مرورگر سیستم skip شد. pip check، بررسی syntax پایتون 3.10 و git diff --check موفق بودند. کتابخانه جدیدی برای این قابلیت اضافه نشده است. هیچ پیام واقعی تلگرام ارسال نشد و SQLite Production تغییر نکرد.

پس از نصب مجاز، با حساب آزمایشی پیام پشتیبانی بفرستید و این موارد را تأیید کنید: ریپلای مستقیم به کاربر درست، پاسخ از دکمه، فرمان ID، username معتبر و عدم ارسال روی username نامعتبر. سپس موجودی و سفارش‌ها را بررسی کنید. پیام خصوصی کاربران یا آرشیو دیتابیس را برای گزارش تست عمومی نکنید.

## نصب جداگانه

تغییر اجرایی شامل app/handlers/support.py، app/db/support_repo.py، app/db/schema.sql و ثبت handlerها در app/main.py است. فقط یک فایل support.py را روی نسخه قدیمی کپی نکنید؛ بدون schema و routing جدید کامل کار نمی‌کند. init_db هنگام startup دو جدول را ایجاد می‌کند. برای نصب، بسته و staging تازه همراه backup و پذیرش لازم است؛ source یا venv stage فعال Production را درجا تغییر ندهید. نصب‌کننده‌های قدیمی و verifier pin‌شده ۱۳۵ تستی، ابزار انتشار خودکار این نسخه جدید نیستند.
